## はじめに

この記事の7つの設定を見直すと、Claude Codeが知らないうちに消費しているトークンの原因を設定レベルで減らせる。

[基礎編](claude-code-cost-management)で扱った `/compact` や `/clear` といった日常的なコスト管理術は、ここでは繰り返さない。モデルの料金プランの選び方や、他社ツールとの料金比較も扱わない。

:::message
**この記事の前提**
- [基礎編](claude-code-cost-management)の内容を理解している
- Claude Code をある程度使い慣れている
- コストの仕組み（トークン消費）を理解している
:::

---

## コストが膨らむ3つのパターン

設定を見直す動機として、コストが膨らみやすい典型パターンを挙げる。

| パターン | 原因 |
|------|------|
| 長時間のデバッグセッション | コンテキスト肥大化に気づかず継続する |
| auto-compact の繰り返し | コンパクト→復元→コンパクトの繰り返しでトークンを消費し続ける |
| Agent Teams の並列実行 | サブエージェントがそれぞれ独立してトークンを消費する（6章で詳述） |

どれも「設定を知らない」だけで起こりうる。以下の7つの設定で予防できる。

---

## 1. MCPサーバーの隠れたコスト

MCPサーバーは便利だが、**接続しているだけでトークンを消費する**。

### なぜコストが発生するのか

MCPサーバーを接続すると、そのサーバーが提供する「ツール定義」がコンテキストの消費につながる。ただし現行のClaude Codeでは、ツール定義は既定で遅延ロードされる。使うときまで中身を読み込まないので、接続しただけで定義の全文が毎回入るわけではない（出典: [Manage costs effectively](https://code.claude.com/docs/en/costs)の「Reduce MCP server overhead」）。

それでも、ツール名などの一覧は残る。使わないサーバーを外せば、その分の消費を減らせる。

### 対策

**使わないMCPサーバーは外す**。必要な時だけ接続する。

```bash
# 現在の接続を確認
claude mcp list

# 不要なサーバーを削除
claude mcp remove サーバー名
```

**CLI代替があるならCLIを使う**。GitHub操作は MCP サーバーよりも `gh` コマンドの方がコンテキスト効率が良い。

| 操作 | MCPサーバー | CLI代替 |
|------|-----------|---------|
| GitHub | MCP GitHub Server（14K+トークン/リクエスト） | `gh` コマンド（0トークン） |
| ファイル検索 | MCP Filesystem Server | Claude Code内蔵のGlob/Grep |
| Web検索 | MCP Web Search | Claude Code内蔵のWebSearch |

## 2. Skills分離で98%トークン削減

CLAUDE.md に全ルールを書き込むと、その全行が毎リクエスト読み込まれる。

基礎編で「CLAUDE.md は短くする」と書いたが、ではルールをどこに書くのか。答えは **Skills**（スキル）だ。

### CLAUDE.md vs Skills

| | CLAUDE.md | Skills |
|---|-----------|--------|
| 読み込みタイミング | **毎リクエスト** | **必要な時だけ** |
| コスト影響 | 1行増える = 全リクエストのコスト増 | 使わない限りゼロ |
| 向いている内容 | プロジェクト全体の基本ルール | 特定タスク用の詳細ルール |

### 具体例

例として、「コミットメッセージの書き方」が50行あるとする。

**CLAUDE.md に書いた場合**：ファイルを読むだけのリクエストでも50行分のトークンを消費する。

**Skillsに分離した場合**：`/commit` を実行した時だけ読み込まれる。それ以外のリクエストでは消費ゼロ。

公式ドキュメントによると、CLAUDE.md は **200行未満** が目安（出典: [Memory](https://code.claude.com/docs/en/memory)）。なお、500行以下が目安なのは Skills の `SKILL.md` のほうだ。CLAUDE.md に収まらないルールは Skills に移動すべき。

## 3. Hooksでログフィルタリング

[Hooks](claude-code-auto-format-hooks)を使って、不要なツール出力をフィルタリングできる。

### なぜ効果があるのか

Claude Code がツールを実行すると、その**出力全体がコンテキストに入る**。`git log` の結果が500行あれば、500行分のトークンを消費する。

Hooks の `PostToolUse` で出力を加工し、必要な部分だけを残すことで、**90〜99%のトークン削減**が可能。

### 設定例：Bash出力の行数制限

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_output' | head -50"
          }
        ]
      }
    ]
  }
}
```

この設定で、Bash コマンドの出力が**最大50行に制限**される。`git log` やテスト結果の出力が数百行になっても、50行しかコンテキストに入らない。

## 4. `/compact` の最適タイミング

基礎編では「長い会話の途中で `/compact`」と書いた。ここでは最適なタイミングを示す。

### 自動コンパクトは遅すぎる

自動コンパクトが発動する大きさは `/autocompact` で設定する（出典: [Model configuration](https://code.claude.com/docs/en/model-config)）。ただし80%を超えたあたりから、すでにパフォーマンスが低下し始める。

**推奨**：コンテキストの **50〜70%** 時点で手動 `/compact` を実行する。

### どうやって50〜70%を知るか

正確な数値を知る方法は限られるが、以下が目安になる：

- **20回以上やり取りした**：ほぼ確実に50%を超えている
- **大きなファイルを複数読ませた**：一気に消費する
- **Claudeの応答が遅くなった**：コンテキスト肥大化のサイン

迷ったら `/compact` して損はない。

## 5. `/rewind` と `Summarize from here` の活用

会話の途中で「ここから先は間違った方向に行った」と気づくことがある。

### `/rewind`

会話を**特定のポイントまで巻き戻す**コマンド。間違った試行錯誤を**なかったことにできる**。

```
/rewind
```

直近の会話を巻き戻すピッカーが表示される。

### `Summarize from here`

巻き戻した後、それまでの会話を要約させる。これにより：

- 間違った試行錯誤が**コンテキストから消える**
- 正しい情報だけが残る
- `/clear` と違い、有用な情報を**保持したまま**リセットできる

`/clear` は「全部忘れる」、`/rewind` + 要約は「失敗だけ忘れる」。

## 6. Agent Teamsのコスト構造を理解する

Claude Code の Agent Teams（サブエージェント並列実行）は強力だが、コストも高い。

### なぜ7倍になるのか

Agent Teams では複数のサブエージェントが**それぞれ独立したコンテキスト**を持つ。つまり：

- メインエージェント：1コンテキスト分のコスト
- サブエージェント×N：各1コンテキスト分のコスト
- **合計 = (1 + N) × 単体コスト**

3つのサブエージェントを並列で動かすと、単純計算で4倍。公式ドキュメントによると、プランモードのチームメイトを使う場合は、通常のセッションの**約7倍**のトークンを使う（出典: [Manage costs effectively](https://code.claude.com/docs/en/costs)）。

### いつ使うべきか

| 状況 | 判断 |
|------|------|
| 明確に独立したタスクが複数ある | 使う価値あり |
| 急いでいないが正確さが必要 | 直列で十分 |
| コスト重視 | 直列で1つずつ |

## 7. Boris Chernyが大きいモデルを使う理由

Claude Code の開発者 Boris Cherny は、自分が Opus を使う理由を X にこう書いている（[2026-01-02の投稿](https://x.com/bcherny/status/2007179838864666847)）。

> it's bigger & slower than Sonnet, since you have to steer it less and it's better at tool use, it is almost always faster than using a smaller model

1回の応答は遅くても、指示の手直しが少なく、ツールの使い方もうまいので、作業が終わるまでの時間は小さいモデルより短くなることが多い、という意味だ。費用については、同じ日の別の投稿で、思考を使わない場合や Opus を使わない場合と比べて「費用と待ち時間の両方が減る」と書いている（[2026-01-02の投稿](https://x.com/bcherny/status/2006972037697569146)）。

試行回数で単純計算すると、次の差になる。

| アプローチ | トークン消費（単純計算） |
|-----------|------------|
| 安いモデルで試行 → 失敗 → 修正指示 → 再試行（×3回） | **4倍以上** |
| 高性能モデルで一発正解 | **1倍** |

**具体的な行動**：

1. **指示を明確にする**（基礎編テクニック3）。曖昧な指示での失敗が最大のコスト
2. **Plan Mode で設計を確認してから実装**（基礎編テクニック5）。やり直しを防ぐ
3. **モデルの知能を信じて、十分な情報を与える**。情報不足が試行錯誤の原因

「ケチって小さいモデルにする」よりも「正確な指示で一発で終わらせる」方がトータルコストは低い。

## コスト最適化チェックリスト

| チェック項目 | 確認方法 |
|------------|---------|
| 不要なMCPサーバーが接続されていないか | `claude mcp list` |
| CLAUDE.md が200行以上になっていないか | `wc -l CLAUDE.md` |
| 特定タスク用ルールがSkillsに分離されているか | `.claude/skills/` を確認 |
| `/compact` を50〜70%時点で実行しているか | 20回以上やり取りしたら実行 |
| Agent Teams を不必要に使っていないか | 直列で十分か検討 |

## 7つの設定の効果

この7つを見直すと、使っていない機能や不要なコンテキストにトークンを使う量が減る。

| 設定 | 期待効果 |
|------|---------|
| MCP接続を最小化 | リクエストあたり14K+トークン削減 |
| Skills分離 | 不使用時のトークン消費ゼロ |
| Hooksでログ制限 | 出力の90〜99%をカット |
| `/compact` を早めに実行 | パフォーマンス低下前にリセット |
| `/rewind` で失敗を巻き戻す | 不要なコンテキストを除去 |
| Agent Teams を慎重に使う | プランモードのチームメイトで約7倍になるコスト増を回避 |
| 一発正解を狙う | 試行錯誤の繰り返しを防止 |

基礎編の内容（`/compact`、`/clear`、具体的な指示）は全員に必要な基本。この上級編は、それでもコストが気になる場合に読む。自分の使い方を振り返り、該当するものから試してみてほしい。
